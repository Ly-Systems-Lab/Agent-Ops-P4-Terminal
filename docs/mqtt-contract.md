# P4 终端 ↔ Agent 侧 MQTT 契约

> 本文是**契约文档**，不是实现代码。它定义设备与 Agent 侧之间交换的主题名、字段名、数据类型与语义。
> 固件按本文写死解析；任何漂移都会表现为「屏幕上一直转圈」或「回执串行错乱」，而且排查要跨两台设备、两种语言。
>
> 实现自主权留给 Agent 侧：语言、进程守护、目录结构、日志方案由你决定。
> **第 4、5、11 节是唯一不可改动的部分。**

---

## 0. 设备在链路里的位置

链路（P4 发起）：

```
P4 的 Hub app ──MQTT publish──> broker ──> Agent 适配器
                                              │
                    ┌─────────────────────────┴──────────────────────────┐
                    ▼                                                    ▼
        流式回执发回 P4                                     需要时转发给其他端侧设备
        hub/chat/p4/reply                                  hub/command/<device>
```

**定位**：这**不是闲聊窗口**（纯闲聊用设备上的小智 AI 即可）。它的用途是**对 Agent 下指令、看结果**。
所以回执的第一要求是「**看得懂、知道成没成**」，不是信息密度。

## 2. 安全边界

P4 是**常驻在局域网里的设备**。一旦 broker 暴露到公网，任何人都能对你的 Agent 下指令。

- **broker 只监听局域网**，绝不做端口转发。
- **必须开 `password_file` + ACL**，禁止 `allow_anonymous`。
  建议每台设备一个独立账号，这样某个客户端出问题时可以单点吊销。
- **ACL 按主题收窄**，不要图省事给 `#`：
  - 设备账号：**可发布** `hub/chat/p4`、`hub/device/p4/status`、`hub/command/p4/ack`；
    **可订阅** `hub/chat/p4/reply`、`hub/command/p4`
  - Agent 适配器账号：`hub/chat/p4` 可读、`hub/chat/p4/reply` 可写；`hub/device/p4/status` 可读；
    `hub/command/p4` 可写、`hub/command/p4/ack` 可读
  - 调试账号：只读 `hub/#`（自验用，用完可以删）
  - ⚠️ **反控那两行不加，设备就收不到命令**：MQTT 3.1.1 下订阅一个被 ACL 拒的主题，
    broker 会拒绝该订阅（mosquitto 默认还会**直接断连**）⇒ 现象是"反复重连、没有明确报错"。
    **遇到反复重连先查这两行。**
- ✅ **加密：TLS 1.2+ + 双向认证（客户端证书）**，端口 **8883**；1883 明文口只绑回环、局域网不可达。
  设备侧证书的生成与放置见 [`secrets/README.md`](../secrets/README.md)。

> 固件当前的行为：证书缺失时照常启动，Hub 顶栏显示「缺证书」，不发起连接。
> 证书不匹配 / 未携带客户端证书时，broker 会**无提示地断连**。

## 3. 连接参数（由 P4 发起）

| 项 | 值 | 备注 |
|---|---|---|
| `client_id` | `p4-<MAC 后 6 位小写 hex>`，如 `p4-a1b2c3` | 稳定不变，可用来做白名单 |
| `clean session` | `true` | **设备不做离线消息堆积**，见 §5.4 第 3 条 |
| `keepalive` | 60 s | |
| 协议版本 | MQTT 3.1.1 | |
| QoS | **一律 1** | 不用 QoS 2 |
| 主题前缀 | `hub/` | 设备侧可配置，**默认 `hub/`** |
| 设备 ID | `p4` | 将来加别的设备时，请把 device id 做成参数，别硬编码进逻辑 |

**上线 / 下线**（P4 自己维护）：

```
上线：publish hub/device/p4/status  retain=true  QoS1
      {"v":1,"online":true,"client_id":"p4-a1b2c3"}

遗嘱（LWT）：broker 在 P4 异常掉线时自动代发，retain=true
      {"v":1,"online":false,"client_id":"p4-a1b2c3"}
```

当前固件只发这两个字段。对端请**忽略不认识的字段** —— 后续版本可能增加 `fw`（固件版本标签）
与 `ts`（Unix 秒），它们仅供参考，不要用来分支逻辑。

设备侧配置项（Hub 的「连接设置」浮层，存 NVS）：主机、端口、用户名、密码、是否加密。
端口随加密开关走（明文 1883 / TLS 8883）。

## 4. 主题契约

| 方向 | 主题 | QoS | retain | 用途 |
|---|---|---|---|---|
| P4 → Agent | `hub/chat/p4` | 1 | **否** | 用户发出的指令 |
| Agent → P4 | `hub/chat/p4/reply` | 1 | **否** | Agent 回执（支持流式分片） |
| P4 → Agent | `hub/device/p4/status` | 1 | **是** | 在线状态 + 遗嘱 |
| Agent → P4 | `hub/command/p4` | 1 | 否 | **反控命令**（见 §11） |
| P4 → Agent | `hub/command/p4/ack` | 1 | 否 | 命令执行回执 |
| P4 → 其他设备 | `hub/command/<target>` | 1 | 否 | 预留 |
| 其他设备 → P4 | `hub/command/<target>/ack` | 1 | 否 | 预留 |

- **`hub/chat/*` 一律不设 retained。** 设了会让 P4 一开机就重放上一条旧回复，
  用户会看到一条莫名其妙的"历史回执"。
- `hub/device/p4/status` 用 retained 是**故意的**：这样你重启后一订阅就知道 P4 在不在。

## 5. 报文契约

通用规则：

- 一律 **UTF-8 原文**，**不要用 `\uXXXX` 转义**（同样的中文，转义后字节数膨胀 ~3 倍，会撞 §5.4 的上限）。
- JSON **扁平，不要嵌套**（除了 `error` 这个对象）。P4 侧用**定长缓冲**解析（MQTT 回调里不分配动态内存），
  嵌套越深越容易出事。
- 字段名**全小写**。每条报文都带 `"v":1`。

### 5.1 P4 → Agent：用户指令

```json
{"v":1,"id":"p4-000123","ts":1730000000,"text":"把客厅的灯关掉"}
```

| 字段 | 类型 | 说明 |
|---|---|---|
| `id` | string | P4 生成，**单次开机内唯一、递增**。格式不保证，**不要解析它，只回传** |
| `ts` | number | Unix 秒。P4 开机时经过 SNTP 对时；未对时也不影响，仅用于日志 |
| `text` | string | 用户指令原文。**中文，可能有错别字**（见 §9） |

### 5.2 Agent → P4：流式回执

一条回执由 **1~N 帧**组成，最后必须有一帧 `final:true`：

```json
{"v":1,"id":"p4-000123","seq":0,"delta":"好的，","final":false}
{"v":1,"id":"p4-000123","seq":1,"delta":"客厅灯已经关了。","final":true}
```

| 字段 | 类型 | 说明 |
|---|---|---|
| `id` | string | **必须与请求逐字符相同**。P4 用它配对，配不上就**静默丢弃** |
| `seq` | number | 同一个 `id` 内从 **0** 开始、严格 +1。乱序或跳号不影响显示，但**影响排错** |
| `delta` | string | **本帧新增的文本**（增量，不是全量）。可以为空串，用于保活 |
| `final` | bool | `true` = 这条回执结束 |

**P4 的显示行为**：发出后立刻出现一个 `...` 气泡；每收到一帧就把 `delta` **追加**到气泡里；
收到 `final:true` 才落盘为一条正式历史。所以在 `final` 之前，用户看到的是"文字在长出来"。

### 5.3 Agent → P4：错误回执

```json
{"v":1,"id":"p4-000123","seq":0,"final":true,
 "error":{"code":"agent_timeout","msg":"Agent 60 秒未响应"}}
```

- `error` 是**对象**，两个必填字段。P4 会把它显示成 `错误：<code> <msg>`。
- 一旦发 error，**必须同时 `final:true`**，并且**不要再发这个 `id` 的任何后续帧**。
- 错误码只用下面四个（新码需要固件侧加处理分支）：

| code | 什么时候用 |
|---|---|
| `agent_timeout` | Agent 超时、放弃 |
| `agent_busy` | 当前忙不过来，明确拒绝（**不是**排队） |
| `bad_request` | 报文不合法：`v` 不是 1、`text` 为空、超长 |
| `internal` | 其他任何内部错误 |

### 5.4 五条硬约束（违反任何一条都会在屏幕上以"看不懂"的形式出现）

1. **单条报文 ≤ 4 KB（UTF-8 字节，不是字符数）。**
   设备接收缓冲 8 KB，留了一倍余量；超过它的报文会被**整条丢弃**（只打一行日志），
   用户那边表现为气泡永远停在 `...`、直到超时。中文 1 字 = 3 字节，4 KB ≈ 1,300 字。
   **请在发送前自己检查字节数**，超了就在自己的侧切片。
2. **`id` 必须原样回传。** 这是唯一能把回执和气泡对上号的东西。
3. **断连期间不排队。** P4 发失败会直接告诉用户"未发送（离线）"，**恢复后不补发**。
   Agent 侧也不需要为它保留待投递队列 —— 断连时入队的消息会在恢复瞬间一次性推出去，变成一堆重复告警。
4. **`final:true` 恰好一次。** 一条 `id` 只能有一个终结（正常或错误二选一）。
   多发 `final` 会让 P4 把同一条内容重复落盘。
5. **QoS 1 意味着"至少一次"，可能收到重复。**
   - 收到重复的 `hub/chat/p4`（同一个 `id`）⇒ **按 `id` 去重，不要重复执行指令**。
     建议维护最近 200 个 `id` 的环形表，带时间淘汰。
   - 发出的回复对 P4 重复一次无伤大雅（重复的 `delta` 会显示成重复字），但**请别靠 broker 去重**。

### 5.5 超时规则

- **设备侧当前没有回执超时。** 发出一条指令后立刻出现 `...` 气泡，它会一直保留到该 `id` 的
  `final:true`（正常或错误）到达为止 —— 设备不会自动放弃，也不会替用户重发。
- ⇒ **对端必须保证每个 `id` 最终都有且只有一个 `final:true`。** 这是本契约里对端唯一
  无法推卸的责任：漏发 `final` 的直接后果是屏幕上那个气泡永远停在 `...`，
  用户没有任何办法从界面上清掉它（只能重启或清空历史）。
- 长任务建议**每 20~30 秒发一帧 `{"v":1,"id":"...","seq":N,"delta":"","final":false}`**：
  它不会改变任何状态，但能让串口日志和用户屏幕都对得上"它还在跑"。
- 如果确实做不完，**发一个 error 回执**（§5.3）比沉默到底好得多 ——
  用户至少知道该怎么处理。

## 6. 内容格式（P4 的渲染限制）

P4 的聊天气泡是 **LVGL 的纯文本 label**，不是浏览器：

- ❌ **不要 Markdown**。`**粗体**`、`# 标题`、`- 列表`、``` 代码块 ``` 会**原样**显示成符号。
- ❌ **不要 emoji**。字库里没有 emoji 字形，会画成一排方框。
- ✅ **可以用 `\n` 换行**。
- ✅ 建议**单条回复 ≤ 300 汉字**。屏幕 10.1" 1280×800，20 px 字，气泡占列表宽度 74%。
  要说的多就**分几帧发**（天然适合流式）。
- ❌ 不要发 base64、图片、二进制、多层嵌套 JSON —— P4 不会解释它们，只会把原始字串显示出来。
- 数字、单位用半角更整齐（`2.5 s` 而不是 `２．５ 秒`）。

**回执的语气建议**（产品定位，不是技术约束）：

- 第一句就说**成没成**："已关闭" / "没找到这个设备"。
- 失败了要给**下一步**："客厅灯没有响应，可能是离线了，要不要我重试？"
  用户没法在 P4 上自己排查，只能靠你告诉他能做什么。
- 不要复述用户的指令（屏幕上就在上面一行）。

## 7. 自验清单（在接设备之前做完）

用一个命令行客户端假扮 P4，先把 broker 与 Agent 侧跑通。

下面的例子按**明文 1883** 写，便于先在本地把链路跑通；正式部署时把
`-p 8883 --cafile ca.crt --cert agent.crt --key agent.key` 加上即可（见 [`secrets/README.md`](../secrets/README.md)）。

```bash
# broker 必须监听局域网，不是 127.0.0.1
ss -tlnp | grep 1883

# 匿名必须被拒绝
mosquitto_pub -h <broker-ip> -t hub/chat/p4 -m 'x'

# 假扮 P4 发一条指令
mosquitto_pub -h <broker-ip> -u p4 -P '<password>' -q 1 -t hub/chat/p4 \
  -m '{"v":1,"id":"p4-test-001","ts":1730000000,"text":"把客厅的灯关掉"}'

# 看回复
mosquitto_sub -h <broker-ip> -u observer -P '<password>' -q 1 -t 'hub/chat/p4/reply' -v

# 联调时看两边的完整对话
mosquitto_sub -h <broker-ip> -u observer -P '<password>' -t 'hub/#' -v
```

| 场景 | 期望 |
|---|---|
| 正常指令 | 收到若干帧，`seq` 从 0 递升，最后一帧 `final:true`，`id` 逐字符回传 |
| 重复投递同一 `id` | 指令**不会被执行两次** |
| `text` 为空串 | 回 `bad_request` + `final:true` |
| 报文 `v` 是 2 | 回 `bad_request` + `final:true` |
| Agent 故意慢 90 秒 | 期间每 20~30 s 有保活帧，最终正常 `final`（而不是静默） |
| Agent 抛异常 | 回 `internal` + `final:true`，**进程不崩** |
| 单帧超过 4 KB | 发送侧就不该发出这么长的帧，自测切片是否正确 |
| `hub/device/p4/status` | 是 retained，订阅后能立刻拿到当前状态 |
| `hub/chat/*` | **不是** retained（新订阅者收不到旧消息） |
| Agent 进程停掉 | broker 仍在，`mosquitto_pub` 不报错；没人回复时那个 `...` 气泡会一直留着 —— 这是可接受的降级，**不要挂一个假应答** |

## 9. 容易踩错的六条

1. **把 P4 当浏览器。** Markdown / emoji 都会原样显示，第 6 节是硬限制。
2. **以为 P4 会补发。** 断连就是失败，用户会看到"未发送（离线）"。
3. **只发 `delta` 不发 `final`。** 设备不会超时放弃，气泡会永远停在 `...`；做不完就发 `error`。
4. **`final:true` 发两次。** P4 会落盘两条重复历史。
5. **报文超 4 KB。** 超过的被整条丢弃，用户只看到卡住的 `...`，没有任何错误提示。
6. **把 `id` 当字符串解析。** 它只是个不透明的配对键。

另外两条与内容相关：

- **P4 的输入能力有限**：拼音只能逐字选，用户很可能打出"把客厅的等关调"这种错字。
  **请对错别字宽容**，必要时反问确认，而不是直接报"没有这个设备"。
- **用户看不到你的日志。** 要让他知道"在做了"，唯一的手段就是发帧。**沉默 = 卡死**，在他眼里两者没有区别。

## 11. 反控命令

> 定位：**验证设备能被 Agent 驱动**，不是"通用远程控制"。
> 设备侧实现见 `components/brookesia_hub_commands/`。

### 11.1 三条固定命令

Agent → P4：`hub/command/p4`，QoS 1，**不要 retained**。

```json
{"v":1,"id":"pi-0001","cmd":"music"}                  # 打开 + 播第 1 首
{"v":1,"id":"pi-0002","cmd":"music","arg":"open"}     # 只打开，不出声
{"v":1,"id":"pi-0003","cmd":"music","arg":"close"}    # 关掉，回桌面（音乐停）
{"v":1,"id":"pi-0004","cmd":"aichat"}                 # 打开小智
{"v":1,"id":"pi-0005","cmd":"aichat","arg":"close"}   # 关掉小智，回桌面
{"v":1,"id":"pi-0006","cmd":"close_all"}              # 一键清理所有后台
```

| `cmd` | 正向 | 反向 |
|---|---|---|
| `music` | 省略 / `arg:"play"` = 打开**并播第 1 首**；`arg:"open"` = 只打开不出声 | `arg:"close"`（或 `"stop"`）= **关掉回桌面，音乐停** |
| `aichat` | 省略 / `arg:"open"` = 打开小智，会话由它自己准备 | `arg:"close"`（或 `"stop"`）= **关掉回桌面，会话结束** |
| **`close_all`** | 无（`arg` 必须省略） | **把所有正在运行的 app 全部关掉**，屏幕回桌面 |

**`close_all` = 最近任务里那个垃圾桶**，逐个 app 发同一条 `STOP` 事件；
效果是"一键释放后台"：音乐停、小智会话断、相机/相册/视频等一并退出。
它**不受**当前有没有前台 app 影响，并且**幂等**：没有 app 在跑时回 `ok:true` + `"closed":0`。

**`close` 的确切语义 = 最近任务里点那个垃圾桶**：走框架同一条 `STOP` 事件 →
`App::processClose()` → 各 app 的 `close()`（音乐是 `audio_player_pause()` + 释放播放器）
⇒ **即使音乐在后台放着，也会真停**，不是"只把界面关掉"。

⚠️ `close` 是**幂等**的：app 本来就没在运行 ⇒ 回 `ok:true`，不报错。

- `id` **建议必带**：ack 原样回传，没有它就无法配对。
- 未知 `cmd` ⇒ 回 `unknown_cmd`，**不做任何事**（不会去开别的 app）。
- **同一 `id` 重复投递不去重**：两条命令本身幂等（app 已开着就 resume），
  重复最多是"又从头播了一遍第 1 首"。要准就别重发。

### 11.2 ack

P4 → Agent：`hub/command/p4/ack`，QoS 1，不 retained。

```json
{"v":1,"id":"pi-0001","cmd":"music","ok":true}
{"v":1,"id":"pi-0003","cmd":"aichat","ok":false,"error":"not_installed"}
{"v":1,"id":"pi-0006","cmd":"close_all","ok":true,"closed":3}
```

`closed` 字段**只有 `close_all` 会带**（这一下清掉了几个 app）；其余命令不带。

| `error` | 含义 |
|---|---|
| `unknown_cmd` | 不是 `music` / `aichat` / `close_all` |
| `bad_arg` | `arg` 不认识（只支持 `play` / `open` / `close`，`stop` 是 `close` 的别名） |
| `not_installed` | 桌面上找不到该 app |
| `event_failed` | 给框架发 START / STOP 事件失败 |
| `start_failed` | 事件发出去了，但 app 没进运行表（真启动失败） |
| `close_failed` | 事件发出去了，但 app 还在运行表里（`close_all` 只要还剩一个就报这个） |
| `no_track` | MusicPlayer 开了，但一首歌都没扫到 |
| `busy` | 命令队列满（Agent 连发太快） |

⚠️ **`ok:true` = "命令已执行到位"**（app 已打开、播放请求已发出），**不是"正在出声"**。
播放是异步的；真失败时设备串口会打 `Failed to start track`。

⚠️ **断连期间不排队**（与聊天同一条契约）：没连上就收不到，连上后也**不会补执行**。

### 11.3 验收

```bash
mosquitto_pub -h <broker> -p 8883 --cafile ca.crt --cert agent.crt --key agent.key -q 1 \
  -t hub/command/p4 -m '{"v":1,"id":"t1","cmd":"music"}'

mosquitto_sub -h <broker> -p 8883 --cafile ca.crt --cert agent.crt --key agent.key -q 1 \
  -t hub/command/p4/ack -v
```

**判据**：发完 `music` 后设备屏幕**自己**切到音乐页并开始响，同时收到 `ok:true`。
`aichat` 同理（屏幕切到小智）。

反向也要验：

```bash
# 先让音乐在后台放着（上滑回桌面），再发这条 ⇒ 声音必须停
mosquitto_pub ... -t hub/command/p4 -m '{"v":1,"id":"t3","cmd":"music","arg":"close"}'
mosquitto_pub ... -t hub/command/p4 -m '{"v":1,"id":"t4","cmd":"aichat","arg":"close"}'
# 再开两三个 app，然后一键清（回执里看 closed 等于几个）
mosquitto_pub ... -t hub/command/p4 -m '{"v":1,"id":"t5","cmd":"close_all"}'
```

**判据**：`music close` 之后**后台也听不到声音了**（不是"界面关掉但还在放"）；
再发一次同一条命令也应回 `ok:true`（幂等）。

### 11.4 已知边界

- **只有这三条**：没有"打开任意 app / 点任意按钮 / 调音量"。
- **music 与 aichat 别同时用**：MusicPlayer 进后台**故意不断音频**，
  两路会同时抢同一个音频编解码通路。**分开测**。
- 运行中的 app 上限是 **3**；开满后再开新的，框架会关掉一个 —— 关的是它内部表顺序里的
  "最后一个"，**不保证最老**。所以别在满 3 个时指望 MusicPlayer 还在放。
